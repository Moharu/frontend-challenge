# Contratos de transporte REST

Os tipos ficam em `src/contracts`, agrupados por recurso, sem dependências de framework, cliente ou mocks. Este é um contrato proposto para etapas futuras; **estão implementados os GET de NFT (listagem, detalhe e relacionados), o carrinho (visitante e conta) e cadastro/login/sessão**. Os demais recursos não possuem handler, estado de teste ou função de API no cliente. Caminhos não suportados sob a API configurada retornam JSON `501 NOT_IMPLEMENTED`, inclusive operações de escrita, em vez do HTML da SPA com status de sucesso.

O envelope compartilhado de erros já foi definido: `{ error: { code, message, fields?, retryable } }`. `fields` associa nomes de campos a **mensagens legíveis e seguras para exibição**, nunca a valores soltos (por exemplo, `fields.quantity: "É possível adicionar no máximo 2."`). Nenhum dado estruturado adicional é enviado no erro: a interface exibe `message` e, após um conflito, obtém o máximo atual de `maxQuantity` na linha do carrinho buscado de novo. Na implementação atual, são exercitados **400 de validação** (consulta, quantidade, cupom), **401 `VISITOR_INVALID`** para token de visitante desconhecido, **401 `INVALID_CREDENTIALS`** no login, **401 `SESSION_INVALID`** para sessão ausente, expirada ou revogada, **404** de NFT/edição/item, **409 `CONFLICT`** de disponibilidade, preço já alterado ou username/e-mail duplicado, **503 transitório** e falha de rede. Erros de permissão (403) continuam apenas previstos. Endpoints ainda não implementados retornam **501 `NOT_IMPLEMENTED`**. A interface pública agora consulta NFTs e conecta o catálogo ao tempo real; recursos privados continuam indisponíveis.

## Convenções compartilhadas

Base: `VITE_API_BASE_URL` (padrão `/api`), resolvida em relação à origem do navegador. Respostas de recurso único: `{ data: T }`. Listas de favoritos/carteiras: `{ data: T[] }`. Paginação de NFTs: `{ data: Nft[], pagination: { page, pageSize, total, pages } }`. Comandos bem-sucedidos propostos sem corpo usam 204. Corpos de requisição em JSON, salvo indicação contrária. IDs são strings opacas; o ID do NFT é diferente do ID da edição. Quantidades, limites de emissão, disponibilidade e versões de recurso são inteiros. As versões começam em 1.

`Eth` é uma string decimal não negativa, com até 18 casas decimais e no máximo 60 dígitos inteiros, sem notação exponencial nem zeros à esquerda, exceto `0`. `ethUnits` a converte em `bigint`, em unidades de 10^-18 ETH; comparação e ordenação de preços nunca usam conversão para ponto flutuante. `normalizeEth` remove zeros decimais redundantes para gerar chaves equivalentes de consulta. A análise de paginação inteira usa números, não o analisador de ETH.

Erros seguem `{ error: { code, message, fields?, retryable } }`, em que `fields` associa nomes de campos a mensagens seguras. Códigos/status estáveis: `VALIDATION`/400, `SESSION_INVALID`/401, `VISITOR_INVALID`/401, `INVALID_CREDENTIALS`/401, `FORBIDDEN`/403, `NOT_FOUND`/404, `CONFLICT`/409, `TRANSIENT`/503, `NOT_IMPLEMENTED`/501. Somente erros HTTP transitórios permitem nova tentativa; falhas de rede não possuem resposta HTTP. Mensagens de erro nunca incluem senhas ou segredos. Os erros de sessão já são simulados; os de permissão abaixo continuam apenas propostos.

## Endpoints de NFT implementados

| Método e caminho | Entradas                     | Sucesso                                           |
| ---------------- | ---------------------------- | ------------------------------------------------- |
| `GET /nfts`      | Parâmetros abaixo, sem corpo | 200 `PageResponse<Nft>`                           |
| `GET /nfts/:id`  | ID do NFT, sem corpo         | 200 `DataResponse<Nft>`; 404 para ID desconhecido |

Campos do NFT: `id`, `name`, `category`, `network`, `artwork`, `createdAt`, `updatedAt`, `version`, `editions`, tokenId, collection, description, fullDescription, gallery, attributes, metadata, discovery e reviews. Cada edição possui `id`, `type` (`unique`, `limited`, `open`), `priceEth`, `supply`, `available`, label e purchaseLimit. `available` fica entre 0 e o limite de emissão. Os valores de arte são identificadores mapeados para arquivos locais autorizados do Figma em `src/components/discovery/assets.ts`. São renderizados nas telas públicas, sem URLs temporárias.

| Parâmetro de consulta  | Padrão   | Validação / semântica                                                                                                                |
| ---------------------- | -------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| `search`               | vazio    | Trecho do nome em minúsculas, sem espaços nas extremidades, no máximo 100 caracteres                                                 |
| `category`             | vazio    | `art`, `music`, `photography`, `3d`, `collectibles`, `generative`, `gaming`, `memberships`, `utility`; vazio significa sem restrição |
| `network`              | vazio    | `ethereum`, `polygon`, `solana`; vazio significa sem restrição                                                                       |
| `minPrice`, `maxPrice` | vazio    | Limites inclusivos em ETH decimal; o mínimo não pode superar o máximo                                                                |
| `sort`                 | `newest` | `newest`, `price-asc`, `price-desc`, `name-asc`                                                                                      |
| `page`                 | 1        | Inteiro de 1 a 1.000.000                                                                                                             |
| `pageSize`             | 8        | Inteiro de 1 a 50                                                                                                                    |

Os filtros são combinados com AND. Filtro e ordenação por preço usam o menor preço entre as edições, inclusive esgotadas: é um preço de referência, não uma cotação disponível para compra. Mudanças de disponibilidade ainda invalidam listas para futuras regras de participação nos resultados. Empates de preço e data usam o ID do NFT em ordem crescente; nomes usam comparação lexicográfica determinística, sem ordenação dependente da localidade. Páginas além do intervalo retornam um array vazio com o total real; um resultado vazio possui zero páginas. Parâmetros desconhecidos, repetidos ou inválidos retornam 400 com erros de campo. As funções de API validam a estrutura da resposta; a entrada das consultas públicas é normalizada pelo mesmo analisador antes da geração da chave.

## Complementação dos campos dos formulários

Esta complementação corrige uma lacuna da especificação anterior: ela proibia consultar o Figma, mas não enumerava todos os campos necessários. Não é uma falha da implementação. A fonte desta atualização é exclusivamente o inventário fornecido pelo usuário; o Figma não foi aberto. Os contratos abaixo continuam **somente definidos**, sem validadores, handlers, autenticação, mutations de conta, checkout ou pedidos.

### Ausência, obrigatoriedade e limpeza

Nos contratos de leitura de conta, perfil, carteira e snapshots de pedido, um campo de dados sem valor é representado por `null`, com a propriedade presente. Entradas de criação omitem campos opcionais; o futuro backend normaliza essas ausências para `null` na leitura. Em atualizações parciais, omitir preserva o valor; enviar `null` limpa um campo anulável. Não usar string vazia como marcador de ausência. Identificadores, versões e campos obrigatórios não aceitam `null`. `declineCode` também é `null` enquanto não houver motivo de recusa. Essas regras não mudam os parâmetros de consulta de NFTs nem a estrutura opcional dos envelopes de erro existentes.

Decisão explícita: **ENS e código de indicação são opcionais**, embora o inventário do Figma os marque com asteriscos. Essa obrigatoriedade não está definida no README do desafio; adotamos a regra solicitada pelo usuário, registrando o desvio do layout. Endereço secundário e observação do colecionador também são opcionais. No cadastro, username, email e password são obrigatórios. Para cadastrar carteira, address, network e provider são obrigatórios; role principal/secundária permanece obrigatório como no contrato anterior. Os dados descritivos da carteira são opcionais. O checkout proposto exige displayName, username, email e profileName no objeto collector, além dos campos existentes de cotação/carteira/rede; os demais dados do colecionador são opcionais. Isso não exige que o perfil já esteja completo imediatamente após o cadastro.

### Cadastro e identidade

`RegisterRequest` recebe somente `username`, `email` e `password`. O formulário não solicita displayName; ele foi retirado da entrada de cadastro e não substitui username. `UserIdentity` contém `id`, `username`, `email` e `displayName: string | null`, permitindo identidade válida logo após cadastro sem nome de exibição preenchido. As duas identidades fictícias usam usernames `ada_example` e `lin_example`; suas credenciais de demonstração estão no README (a seed guarda só sal e hash).

A confirmação de senha é validada somente no cliente e não trafega na API. O mesmo vale para a confirmação da nova senha: `ChangePasswordRequest` mantém somente `currentPassword` e `newPassword`.

### Perfil do colecionador

`Profile` preserva `userId` e `version`, inclui username e email obrigatórios e representa displayName, ensName, walletNickname, bio e avatar como `string | null`. Assim, os campos ainda não preenchidos depois do cadastro podem ser lidos sem inventar valores. `bio` foi preservado do contrato anterior, mas não é exigido pelo inventário do layout. `UpdateProfileRequest` exige version e permite atualizar parcialmente username, email, displayName, ensName, walletNickname e bio. Username/email podem ser omitidos para preservação, mas não limpos com null.

Avatar permanece na leitura do perfil, mas sua alteração usa exclusivamente `UpdateAvatarRequest` no endpoint existente: `dataUrl` é obrigatório, aceita string ou `null` para remover o avatar, acompanhado de version. Senhas permanecem em seu contrato específico; nenhum desses campos integra a atualização genérica de perfil.

### Carteiras e preenchimento do formulário

`Wallet` mantém id, userId, address, network, role e version e acrescenta provider. `WalletProvider` usa identificadores de transporte `metamask`, `walletconnect` e `coinbase-wallet`, apresentados respectivamente como MetaMask, WalletConnect e Coinbase Wallet.

Os campos descritivos de carteira são displayName, **label** (apelido da carteira), profileName, referralCode, email, ensName e secondaryAddressOrEns. Todos aparecem na leitura como string ou null e são opcionais na criação. Não foi criado outro campo walletNickname na carteira: label já tem esse significado. `UpdateWalletRequest` exige version; omitir qualquer campo editável o preserva e null limpa apenas os descritivos anuláveis. Endereço, rede, provedor e role, quando enviados, devem continuar preenchidos; não podem ser limpos.

“Igual à carteira principal” será uma ação futura de preenchimento do formulário, copiando os valores editáveis aplicáveis da principal para os campos do formulário. Não é uma flag persistida nem sincronização contínua entre carteiras. Nenhum comportamento desse controle foi adicionado agora.

### Dados do checkout e snapshots do pedido

`CheckoutCollectorData`, em `src/contracts/checkout.ts`, contém displayName, username, email e profileName obrigatórios e referralCode, ensName e secondaryAddressOrEns opcionais. `CreateOrderBody` contém quoteId, quoteVersion e walletId (a `network` saiu do corpo na etapa de pedidos: vem da carteira, no servidor), acrescentando `collector: CheckoutCollectorData` e `collectorNote?: string`. A chave continua em `CreateOrderRequest.idempotencyKey`, enviada pelo cabeçalho `Idempotency-Key`, sem duplicação no JSON.

`walletId` identifica a carteira cadastrada. O backend simulado resolve address, network e provider a partir dela, verifica sua titularidade e não trata valores editáveis do formulário como fonte confiável para esses dois campos. Por isso, endereço e provedor não são duplicados no corpo do pedido. O formulário pode exibi-los a partir da carteira selecionada; escolher outra carteira altera walletId.

`Order` e `OrderReceipt` compartilham `OrderCheckoutSnapshot`, contendo collector, wallet e collectorNote somente para leitura. O collector guarda os dados efetivamente usados, normalizando os opcionais ausentes para null. O snapshot wallet guarda walletId, walletVersion, address, network e provider resolvidos no momento da criação. A observação ausente é null. Esses retratos são preservados nas transições e no recibo: alterações futuras no perfil ou na carteira não podem alterar um pedido já criado. Os snapshots anteriores de itens e valores permanecem preservados. `order.updated` transporta esses mesmos dados por incluir o Order completo.

**Todos os campos enviados no corpo** participam da comparação de idempotência: quoteId, quoteVersion, walletId, cada campo de collector e collectorNote quando presentes. A futura comparação deve usar uma representação canônica, independente da ordem das propriedades JSON. A mesma chave/corpo recupera o mesmo pedido e seus snapshots existentes, sem reconstruí-los a partir do perfil/carteira atual; qualquer diferença no corpo para a mesma chave gera conflito. Os dados resolvidos pelo backend não são campos extras enviados pelo cliente.

### Propriedade e significado dos campos

| Dados                                                                                             | Recurso responsável                                                                                      | Uso no checkout/pedido                                                                                         |
| ------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| username, email e displayName da conta                                                            | Identidade/perfil do usuário; username e email são preenchidos no cadastro                               | Podem sugerir valores iniciais; collector registra os valores enviados especificamente para a compra           |
| ensName e walletNickname do perfil; bio e avatar                                                  | Perfil do colecionador; bio é legado sem exigência no inventário, avatar usa contrato específico         | Não atualizam carteira nem pedido automaticamente; walletNickname não duplica o campo label dentro da carteira |
| displayName, label, profileName, email, ensName, referralCode e secondaryAddressOrEns da carteira | Dados descritivos da carteira cadastrada; não substituem dados da conta, mesmo quando os nomes coincidem | Podem preencher o formulário; somente os valores efetivamente usados entram no snapshot collector              |
| address, network e provider da carteira                                                           | Carteira cadastrada, identificada por walletId e validada pelo futuro backend                            | address/network/provider são resolvidos pelo backend; os valores resolvidos entram em wallet                   |
| collector do corpo do pedido                                                                      | Dados próprios da compra, não uma mutation de perfil/carteira                                            | Convertidos para snapshot imutável do colecionador                                                             |
| collectorNote                                                                                     | Observação opcional desta compra, sem campo equivalente de perfil/carteira                               | Persistida no snapshot do pedido/recibo ou null                                                                |

Alterar dados no checkout **não atualiza automaticamente o perfil ou a carteira**. Valores iguais entre recursos podem resultar de preenchimento do formulário, não de um vínculo de sincronização. Nenhum estado privado, preenchimento automático, persistência de conta/carteira ou fluxo de compra foi implementado.

## Descoberta pública implementada

Adicionado **GET /nfts/:id/related**: sem corpo ou parâmetros de consulta, retorna 200 `{ data: Nft[] }` com até cinco peças da mesma coleção, excluindo a atual, em ordem estável da seed; NFT inexistente retorna 404. Reviews são conteúdo de leitura incluído no NFT, sem endpoint de envio.

Listagem aceita também **mode** (`all` por padrão, `new`, `trending`). New filtra isNew; trending filtra trendingScore >= 100 e, com sort=newest, prioriza a pontuação decrescente. Ordenações explícitas por preço/nome continuam funcionando dentro do conjunto filtrado. A resposta inclui **facets** com mapas categories/networks, calculados após todos os filtros e antes da paginação; não são contagens globais ou facetas que removem o próprio filtro. A interface não mostra contagens decorativas.

Metadados incluem contrato simulado, padrão, royalty e procedência; discovery inclui indicador determinístico de lançamento, pontuação de popularidade e raridade opcional; avaliações são registros de leitura com autor, nota e conteúdo. Os preços de referência mantêm edições esgotadas no mínimo, enquanto a seleção do detalhe usa disponibilidade e purchaseLimit. Edição aberta tem oferta finita simulada, não quantidade infinita. As três redes usam ETH nesta demonstração.

A API conserva pageSize padrão 8; a interface usa 9 e normaliza parâmetros de URL com recuperação de campos inválidos, sem enfraquecer o parser estrito da API. A semântica completa dos modos, rotas, seed 2, limites e correções do layout está em [descoberta pública](../discovery.md). Conta, favoritos persistidos, carrinho, cotação, pedidos, perfil e carteiras permanecem somente contratos, mesmo quando seus botões aparecem na composição com aviso de indisponibilidade.

## Carrinho do visitante implementado

Todas as rotas (exceto a emissão) identificam o carrinho por `Authorization: Bearer <token de sessão>` ou, sem sessão, pelo cabeçalho `X-Visitor-Token`; a sessão prevalece quando ambos chegam. Respondem `{ data: Cart }`. Token de visitante desconhecido responde 401 `VISITOR_INVALID`; sessão inválida, 401 `SESSION_INVALID`. Tipos e validador em `src/contracts/cart.ts`; regras completas, cupons e decisões em [carrinho](../cart.md).

| Endpoint                     | Requisição                                                   | Resposta                                                                                                                                   |
| ---------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------ |
| `POST /visitor-sessions`     | Sem corpo                                                    | 201 `{ data: { token } }`; token opaco, base da futura mesclagem no login                                                                  |
| `GET /cart`                  | —                                                            | 200 carrinho; 401 `VISITOR_INVALID` / `SESSION_INVALID` para identificação ausente ou inválida                                             |
| `POST /cart/items`           | `AddCartItemRequest`: nftId, editionId, quantity (1..1000)   | 200; soma à linha da mesma edição; 400 quantidade; 404 NFT/edição; 409 esgotada ou acima do limite efetivo, com `fields.quantity` em texto |
| `PATCH /cart/items/:itemId`  | `ChangeCartItemRequest`: quantity? e/ou acknowledgePriceEth? | 200; 400 sem alteração/inválido; 404 item; 409 acima do limite (`fields.quantity` em texto) ou preço reconhecido já desatualizado          |
| `DELETE /cart/items/:itemId` | —                                                            | 200; 404 item                                                                                                                              |
| `PUT /cart/coupon`           | `ApplyCouponRequest`: code                                   | 200; substitui o cupom anterior; 400 `fields.coupon` para vazio, inexistente ou expirado                                                   |
| `DELETE /cart/coupon`        | —                                                            | 200                                                                                                                                        |

`Cart` contém `id`, `version`, `updatedAt`, `items`, `itemCount` (soma das quantidades), `coupon` (somente se válido), `couponRemoved` (`{ code, reason }` quando o cupom aplicado expirou: sem desconto, com o motivo; mesma regra da cotação), `summary` (`subtotalEth`, `discountEth`, `networkFeeEth`, `totalEth`, `feeNetwork`, `feeEstimated`) e `hasConflicts`. Cada `CartLine` expõe nftId/editionId, versão do NFT, nome, arte, tokenId, rótulo da edição, quantidade, preço unitário atual, total da linha, disponibilidade, limite de compra, `maxQuantity`, `priceChange` e `conflict`. Valores são calculados no servidor simulado com `src/contracts/eth.ts`; a interface não recalcula.

## Sessão e conta implementadas

Tipos e validadores em `src/contracts/session.ts`; política completa em [sessão](../session.md). Login e cadastro aceitam o `X-Visitor-Token` opcional para mesclar o carrinho de visitante.

| Endpoint                 | Requisição                                   | Resposta                                                                                                                               |
| ------------------------ | -------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| `POST /account/register` | `RegisterRequest`: username, email, password | 201 `DataResponse<AuthResponse>` (já autenticado, `displayName` nulo); 400 `VALIDATION` por campo; 409 `CONFLICT` para username/e-mail |
| `POST /session/login`    | `LoginRequest`: email, password              | 200 `DataResponse<AuthResponse>`; 401 `INVALID_CREDENTIALS` com mensagem genérica, igual para e-mail desconhecido e senha errada       |
| `GET /session`           | `Authorization: Bearer <token>`              | 200 `DataResponse<Session>`; 401 `SESSION_INVALID` para sessão ausente, expirada ou revogada                                           |
| `POST /session/logout`   | `Authorization: Bearer <token>`, sem corpo   | 204; revoga o token (idempotente) e avança a geração                                                                                   |

`AuthResponse` contém `token` (opaco), `session` (`id`, `user` com id/username/email/displayName, `expiresAt`, `generation`) e `merge` (`addedLines`, `mergedLines`, `conflictLines`, `coupon`, ou `null` quando não houve carrinho de visitante a mesclar). Username e e-mail são normalizados para minúsculas e comparados sem diferenciar maiúsculas. O token em `Authorization` é uma simplificação da simulação; em produção seria um cookie `HttpOnly`, `Secure` e `SameSite`.

## Checkout implementado

Rotas privadas (sessão obrigatória, `Authorization: Bearer`). Tipos e validadores em `src/contracts/wallets.ts`, `src/contracts/quotes.ts` e `src/contracts/checkout.ts`; regras completas em [checkout](../checkout.md).

| Endpoint                      | Requisição                                                                                   | Resposta                                                                                                                                                                                                      |
| ----------------------------- | -------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /wallets`                | —                                                                                            | 200 `{ data: Wallet[] }` (principal primeiro)                                                                                                                                                                 |
| `POST /wallets`               | `CreateWalletRequest`: address, network, provider, label; descritivos opcionais (sem `role`) | 201 `DataResponse<Wallet>`; a primeira carteira vira `primary`, as seguintes `secondary`; 400 `VALIDATION` por campo (endereço por rede, provedor, nome); 409 `CONFLICT` para endereço já cadastrado          |
| `POST /wallet-connections`    | `CreateWalletConnectionRequest`: walletId                                                    | 201 `DataResponse<WalletConnection>` (`id`, `walletId`, `status`, `createdAt`) após latência curta; 409 `CONNECTION_REJECTED` na recusa; 403 carteira de outro usuário; 404 carteira inexistente              |
| `GET /wallet-connections/:id` | —                                                                                            | 200 com `status` `active` ou `disconnected`; 403 / 404                                                                                                                                                        |
| `POST /quotes`                | `QuoteRequest`: cartId, cartVersion, walletId                                                | 200 `DataResponse<Quote>`; 403 carrinho ou carteira de outro usuário; 404 carteira inexistente; 409 `WALLET_DISCONNECTED`, `CART_CHANGED` ou `UNAVAILABLE_ITEMS` (uma mensagem por linha afetada em `fields`) |

`Quote` contém `id`, `version`, `cartId`, `cartVersion`, `walletId`, `network` (da carteira), `expiresAt` (2 minutos pelo relógio real), `items`, `coupon`, `couponRemoved` (`{ code, reason }` quando o cupom do carrinho expirou), `amounts` (subtotal, desconto, taxa da rede da carteira, total). Cotações são persistidas no servidor simulado (as 50 mais recentes). **Regra de versão:** cada emissão recebe um `id` novo; a `version` pertence à série do mesmo usuário, carrinho e carteira e só aumenta quando algum valor (itens, preços, cupom, taxa, total) muda em relação à cotação anterior da série. O cupom é revalidado a cada cotação, inclusive a expiração; quantidades nunca são reduzidas pela API. O cliente pede nova cotação ao confirmar e exige nova confirmação explícita quando qualquer valor muda em relação à cotação exibida.

## Pedidos implementados

Tipos e validadores em `src/contracts/orders.ts`; fluxo e decisões em [pedidos](../orders.md).

| Endpoint                  | Requisição                                                                                                                            | Resposta                                                                                                                                                                                                                                                                                                                                      |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST /orders`            | Cabeçalho `Idempotency-Key` (`[A-Za-z0-9-]`, 16 a 64) + `CreateOrderBody`: quoteId, quoteVersion, walletId, collector, collectorNote? | 201 `DataResponse<Order>` (`pending`); 200 com o mesmo pedido para a mesma chave e o mesmo corpo; 400 sem chave válida ou com `fields` do colecionador; 409 `CONFLICT` para a mesma chave com outro corpo; 409 `QUOTE_CHANGED` com a cotação nova em `error.quote`; 403 / 404; 409 `WALLET_DISCONNECTED`, `CART_CHANGED`, `UNAVAILABLE_ITEMS` |
| `GET /orders/:id`         | —                                                                                                                                     | 200 `DataResponse<Order>`; 403 pedido de outro usuário; 404                                                                                                                                                                                                                                                                                   |
| `GET /orders/:id/receipt` | —                                                                                                                                     | 200 `DataResponse<OrderReceipt>` somente quando `confirmed`; 409 nos demais estados; 403 / 404                                                                                                                                                                                                                                                |

- **Idempotência:** a chave vale por usuário (`userId:chave`). O corpo é comparado pela forma canônica (`canonicalJson`: chaves ordenadas, `undefined` descartado), então a ordem das propriedades não importa. A mesma chave e o mesmo corpo devolvem o pedido já criado, com os snapshots originais, inclusive depois de uma resposta perdida.
- **Comparação da cotação no servidor:** o pedido só é criado se a cotação guardada pertence ao usuário, tem a `version` enviada, não expirou, usa a mesma carteira e a mesma versão do carrinho, e se uma cotação calculada agora tem os mesmos valores. Caso contrário, o servidor emite uma nova cotação (pela regra de versão) e responde 409 `QUOTE_CHANGED` com ela em `error.quote`; o cliente mostra o que mudou e exige nova confirmação.
- **Colecionador:** validado no servidor com `collectorErrors`, as mesmas regras do formulário.
- **Snapshots imutáveis:** itens (nome, edição, `tokenId`, arte, quantidade, preço unitário e da linha), valores (com o código do cupom), colecionador e carteira resolvida são copiados na criação. Mudanças posteriores no catálogo, perfil ou carteira não alteram pedido nem recibo.
- **Estoque:** a criação reserva as quantidades (`available` diminui); a recusa as libera; a confirmação as mantém consumidas.
- **Resolução:** cada pedido guarda `resolveAt` e o resultado simulado; a resolução acontece no servidor simulado (ao ler o pedido ou a cada 250ms), sobrevive a recargas e é aplicada uma única vez. Na confirmação, o recibo recebe `transactionReference` (`0x` + 64 hexadecimais) e o carrinho perde exatamente as quantidades compradas (linhas zeradas saem; linhas acrescentadas depois continuam). Na recusa, `declineCode`/`declineReason` e o carrinho fica intacto.
- **Atualizações privadas:** cada transição emite `order.updated` somente para as conexões autenticadas do dono (ver [eventos](events.md)).
