# Contratos de transporte REST

Os tipos ficam em `src/contracts`, agrupados por recurso, sem dependências de framework, cliente ou mocks. Este é um contrato proposto para etapas futuras; **somente GET de listagem e detalhe de NFT estão implementados**. Nenhum outro recurso possui handler, estado de teste ou função de API no cliente. Caminhos não suportados sob a API configurada retornam JSON `501 NOT_IMPLEMENTED`, inclusive operações de escrita, em vez do HTML da SPA com status de sucesso.

Erros de sessão, permissão e conflito continuam apenas previstos nos contratos. Endpoints ainda não implementados retornam **501 `NOT_IMPLEMENTED`**. Nenhuma dessas operações é chamada automaticamente pela tela provisória.

## Convenções compartilhadas

Base: `VITE_API_BASE_URL` (padrão `/api`), resolvida em relação à origem do navegador. Respostas de recurso único: `{ data: T }`. Listas de favoritos/carteiras: `{ data: T[] }`. Paginação de NFTs: `{ data: Nft[], pagination: { page, pageSize, total, pages } }`. Comandos bem-sucedidos propostos sem corpo usam 204. Corpos de requisição em JSON, salvo indicação contrária. IDs são strings opacas; o ID do NFT é diferente do ID da edição. Quantidades, limites de emissão, disponibilidade e versões de recurso são inteiros. As versões começam em 1.

`Eth` é uma string decimal não negativa, com até 18 casas decimais e no máximo 60 dígitos inteiros, sem notação exponencial nem zeros à esquerda, exceto `0`. `ethUnits` a converte em `bigint`, em unidades de 10^-18 ETH; comparação e ordenação de preços nunca usam conversão para ponto flutuante. `normalizeEth` remove zeros decimais redundantes para gerar chaves equivalentes de consulta. A análise de paginação inteira usa números, não o analisador de ETH.

Erros seguem `{ error: { code, message, fields?, retryable } }`, em que `fields` associa nomes de campos a mensagens seguras. Códigos/status estáveis: `VALIDATION`/400, `SESSION_INVALID`/401, `FORBIDDEN`/403, `NOT_FOUND`/404, `CONFLICT`/409, `TRANSIENT`/503, `NOT_IMPLEMENTED`/501. Somente erros HTTP transitórios permitem nova tentativa; falhas de rede não possuem resposta HTTP. Mensagens de erro nunca incluem senhas ou segredos. Os erros de sessão e permissão abaixo são apenas propostos, ainda não simulados.

## Endpoints de NFT implementados

| Método e caminho | Entradas                     | Sucesso                                           |
| ---------------- | ---------------------------- | ------------------------------------------------- |
| `GET /nfts`      | Parâmetros abaixo, sem corpo | 200 `PageResponse<Nft>`                           |
| `GET /nfts/:id`  | ID do NFT, sem corpo         | 200 `DataResponse<Nft>`; 404 para ID desconhecido |

Campos do NFT: `id`, `name`, `category`, `network`, `artwork`, `createdAt`, `updatedAt`, `version`, `editions`. Cada edição possui `id`, `type` (`unique`, `limited`, `open`), `priceEth`, `supply` e `available`. `available` fica entre 0 e o limite de emissão. Os valores de arte são identificadores locais provisórios, não URLs de imagens remotas. Eles não são renderizados nesta etapa.

| Parâmetro de consulta  | Padrão   | Validação / semântica                                                                |
| ---------------------- | -------- | ------------------------------------------------------------------------------------ |
| `search`               | vazio    | Trecho do nome em minúsculas, sem espaços nas extremidades, no máximo 100 caracteres |
| `category`             | vazio    | `art`, `music`, `photography`; vazio significa sem restrição                         |
| `network`              | vazio    | `ethereum`, `polygon`; vazio significa sem restrição                                 |
| `minPrice`, `maxPrice` | vazio    | Limites inclusivos em ETH decimal; o mínimo não pode superar o máximo                |
| `sort`                 | `newest` | `newest`, `price-asc`, `price-desc`, `name-asc`                                      |
| `page`                 | 1        | Inteiro de 1 a 1.000.000                                                             |
| `pageSize`             | 8        | Inteiro de 1 a 50                                                                    |

Os filtros são combinados com AND. Filtro e ordenação por preço usam o menor preço entre as edições, inclusive esgotadas: é um preço de referência, não uma cotação disponível para compra. Mudanças de disponibilidade ainda invalidam listas para futuras regras de participação nos resultados. Empates de preço e data usam o ID do NFT em ordem crescente; nomes usam comparação lexicográfica determinística, sem ordenação dependente da localidade. Páginas além do intervalo retornam um array vazio com o total real; um resultado vazio possui zero páginas. Parâmetros desconhecidos, repetidos ou inválidos retornam 400 com erros de campo. As funções de API validam a estrutura da resposta; a entrada das consultas públicas é normalizada pelo mesmo analisador antes da geração da chave.

Operações privadas exigem identidade de sessão e retornam 401 na expiração, 403 quando a titularidade não permite acesso e 404 para recursos ausentes. O futuro controlador de cenários de mocks provocará a expiração; não existe endpoint público para expirar sessões. A sessão inclui `id`, identidade do usuário, `expiresAt` e `generation`. A expiração deve preservar o contexto público para retomada; logout/troca de usuário devem descartar assinaturas privadas e limpar caches por usuário. A implementação de cookies e do hash de credenciais está adiada; as identidades de teste não possuem credenciais.

Cotações incluem identidades e versões de carrinho/cotação, validade, versões de NFTs, quantidades/disponibilidade de edições, cupom, subtotal, desconto, taxa de rede, total e `requiresConfirmation`. A API deve revalidar todos os valores e exigir nova confirmação em caso de mudanças. Nenhum cálculo de cotação ou comportamento de cupom está implementado agora.

Pedidos incluem estados `pending`/`confirmed`/`declined`, identidade/usuário/versão, identidade/versão da cotação, retratos de itens e valores comprados, datas/horários e motivo opcional de recusa. Recibos possuem nomes de itens somente para leitura, identidades de NFT/edição, quantidades, valores unitários/por linha, totais, horário de confirmação e referência simulada de transação. Confirmado e recusado são estados terminais. O futuro servidor deve limitar chaves de idempotência ao usuário, comparar corpos canônicos, retornar o mesmo pedido para a mesma chave/corpo, inclusive após timeout, e retornar 409 `CONFLICT` para a mesma chave com corpo diferente. Recibos tornam-se imutáveis na confirmação; alterações posteriores no catálogo não podem modificá-los. Nenhum desses comportamentos está implementado ainda.

## Complementação dos campos dos formulários

Esta complementação corrige uma lacuna da especificação anterior: ela proibia consultar o Figma, mas não enumerava todos os campos necessários. Não é uma falha da implementação. A fonte desta atualização é exclusivamente o inventário fornecido pelo usuário; o Figma não foi aberto. Os contratos abaixo continuam **somente definidos**, sem validadores, handlers, autenticação, mutations de conta, checkout ou pedidos.

### Ausência, obrigatoriedade e limpeza

Nos contratos de leitura de conta, perfil, carteira e snapshots de pedido, um campo de dados sem valor é representado por `null`, com a propriedade presente. Entradas de criação omitem campos opcionais; o futuro backend normaliza essas ausências para `null` na leitura. Em atualizações parciais, omitir preserva o valor; enviar `null` limpa um campo anulável. Não usar string vazia como marcador de ausência. Identificadores, versões e campos obrigatórios não aceitam `null`. `declineCode` também é `null` enquanto não houver motivo de recusa. Essas regras não mudam os parâmetros de consulta de NFTs nem a estrutura opcional dos envelopes de erro existentes.

Decisão explícita: **ENS e código de indicação são opcionais**, embora o inventário do Figma os marque com asteriscos. Essa obrigatoriedade não está definida no README do desafio; adotamos a regra solicitada pelo usuário, registrando o desvio do layout. Endereço secundário e observação do colecionador também são opcionais. No cadastro, username, email e password são obrigatórios. Para cadastrar carteira, address, network e provider são obrigatórios; role principal/secundária permanece obrigatório como no contrato anterior. Os dados descritivos da carteira são opcionais. O checkout proposto exige displayName, username, email e profileName no objeto collector, além dos campos existentes de cotação/carteira/rede; os demais dados do colecionador são opcionais. Isso não exige que o perfil já esteja completo imediatamente após o cadastro.

### Cadastro e identidade

`RegisterRequest` recebe somente `username`, `email` e `password`. O formulário não solicita displayName; ele foi retirado da entrada de cadastro e não substitui username. `UserIdentity` contém `id`, `username`, `email` e `displayName: string | null`, permitindo identidade válida logo após cadastro sem nome de exibição preenchido. As duas identidades fictícias usam usernames `ada_example` e `lin_example` e continuam sem autenticação ou credenciais armazenadas.

A confirmação de senha pertence à validação futura do cliente e não trafega na API. O mesmo vale para a confirmação da nova senha: `ChangePasswordRequest` mantém somente `currentPassword` e `newPassword`.

### Perfil do colecionador

`Profile` preserva `userId` e `version`, inclui username e email obrigatórios e representa displayName, ensName, walletNickname, bio e avatar como `string | null`. Assim, os campos ainda não preenchidos depois do cadastro podem ser lidos sem inventar valores. `bio` foi preservado do contrato anterior, mas não é exigido pelo inventário do layout. `UpdateProfileRequest` exige version e permite atualizar parcialmente username, email, displayName, ensName, walletNickname e bio. Username/email podem ser omitidos para preservação, mas não limpos com null.

Avatar permanece na leitura do perfil, mas sua alteração usa exclusivamente `UpdateAvatarRequest` no endpoint existente: `dataUrl` é obrigatório, aceita string ou `null` para remover o avatar, acompanhado de version. Senhas permanecem em seu contrato específico; nenhum desses campos integra a atualização genérica de perfil.

### Carteiras e preenchimento do formulário

`Wallet` mantém id, userId, address, network, role e version e acrescenta provider. `WalletProvider` usa identificadores de transporte `metamask`, `walletconnect` e `coinbase-wallet`, apresentados respectivamente como MetaMask, WalletConnect e Coinbase Wallet.

Os campos descritivos de carteira são displayName, **label** (apelido da carteira), profileName, referralCode, email, ensName e secondaryAddressOrEns. Todos aparecem na leitura como string ou null e são opcionais na criação. Não foi criado outro campo walletNickname na carteira: label já tem esse significado. `UpdateWalletRequest` exige version; omitir qualquer campo editável o preserva e null limpa apenas os descritivos anuláveis. Endereço, rede, provedor e role, quando enviados, devem continuar preenchidos; não podem ser limpos.

“Igual à carteira principal” será uma ação futura de preenchimento do formulário, copiando os valores editáveis aplicáveis da principal para os campos do formulário. Não é uma flag persistida nem sincronização contínua entre carteiras. Nenhum comportamento desse controle foi adicionado agora.

### Dados do checkout e snapshots do pedido

`CheckoutCollectorData`, em `src/contracts/checkout.ts`, contém displayName, username, email e profileName obrigatórios e referralCode, ensName e secondaryAddressOrEns opcionais. `CreateOrderBody` preserva quoteId, quoteVersion, walletId e network, acrescentando `collector: CheckoutCollectorData` e `collectorNote?: string`. A chave continua em `CreateOrderRequest.idempotencyKey`, enviada pelo cabeçalho `Idempotency-Key`, sem duplicação no JSON.

`walletId` identifica a carteira cadastrada. O futuro backend simulado resolve e valida address e provider a partir dela, verifica sua titularidade e compatibilidade com a network enviada e não trata valores editáveis do formulário como fonte confiável para esses dois campos. Por isso, endereço e provedor não são duplicados no corpo do pedido. O formulário pode exibi-los a partir da carteira selecionada; escolher outra carteira altera walletId. Nenhuma resolução ou validação foi implementada nesta alteração.

`Order` e `OrderReceipt` compartilham `OrderCheckoutSnapshot`, contendo collector, wallet e collectorNote somente para leitura. O collector guarda os dados efetivamente usados, normalizando os opcionais ausentes para null. O snapshot wallet guarda walletId, walletVersion, address, network e provider resolvidos no momento da criação. A observação ausente é null. Esses retratos são preservados nas transições e no recibo: alterações futuras no perfil ou na carteira não podem alterar um pedido já criado. Os snapshots anteriores de itens e valores permanecem preservados. `order.updated` transporta esses mesmos dados por incluir o Order completo; o evento continua sem implementação.

**Todos os campos enviados no corpo** participam da comparação de idempotência: quoteId, quoteVersion, walletId, network, cada campo de collector e collectorNote quando presentes. A futura comparação deve usar uma representação canônica, independente da ordem das propriedades JSON. A mesma chave/corpo recupera o mesmo pedido e seus snapshots existentes, sem reconstruí-los a partir do perfil/carteira atual; qualquer diferença no corpo para a mesma chave gera conflito. Os dados resolvidos pelo backend não são campos extras enviados pelo cliente.

### Propriedade e significado dos campos

| Dados                                                                                             | Recurso responsável                                                                                      | Uso no checkout/pedido                                                                                                    |
| ------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| username, email e displayName da conta                                                            | Identidade/perfil do usuário; username e email são preenchidos no cadastro                               | Podem sugerir valores iniciais; collector registra os valores enviados especificamente para a compra                      |
| ensName e walletNickname do perfil; bio e avatar                                                  | Perfil do colecionador; bio é legado sem exigência no inventário, avatar usa contrato específico         | Não atualizam carteira nem pedido automaticamente; walletNickname não duplica o campo label dentro da carteira            |
| displayName, label, profileName, email, ensName, referralCode e secondaryAddressOrEns da carteira | Dados descritivos da carteira cadastrada; não substituem dados da conta, mesmo quando os nomes coincidem | Podem preencher o formulário; somente os valores efetivamente usados entram no snapshot collector                         |
| address, network e provider da carteira                                                           | Carteira cadastrada, identificada por walletId e validada pelo futuro backend                            | address/provider são resolvidos pelo backend; network enviada deve ser compatível; os valores resolvidos entram em wallet |
| collector do corpo do pedido                                                                      | Dados próprios da compra, não uma mutation de perfil/carteira                                            | Convertidos para snapshot imutável do colecionador                                                                        |
| collectorNote                                                                                     | Observação opcional desta compra, sem campo equivalente de perfil/carteira                               | Persistida no snapshot do pedido/recibo ou null                                                                           |

Alterar dados no checkout **não atualiza automaticamente o perfil ou a carteira**. Valores iguais entre recursos podem resultar de preenchimento do formulário, não de um vínculo de sincronização. Nenhum estado privado, preenchimento automático, persistência de conta/carteira ou fluxo de compra foi implementado.
